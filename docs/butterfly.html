DO-178C structural coverage & object-code evidence

Butterfly

A read-only browser over compiled evidence. Point it at what your compiler, coverage tools and simulator already produced, and it shows — per function — what a reviewer needs for Annex A tables A-5 and A-7. It is not an editor, and it does not run your tests. Its first job is to be honest about what the evidence cannot prove.

What it is

Butterfly reads three things your build already produces and turns them into a reviewable picture of one function at a time.

Everything else — stack usage .su files, build-info.txt, the project config, the analysis baseline, the change-history cache — is discovered automatically when you point ingest at a build directory.

Projected versus measured the central idea

This is the one concept worth understanding before anything else, and it is what separates butterfly from a coverage percentage.

Your coverage tool measured source lines and branches. Your certification authority, at Level A, asks about object code — the instructions that actually ship. Butterfly maps the first onto the second through the DWARF line table. That mapping is a projection, not a measurement: nothing counted those instructions executing.

The consequence

A green instruction means “implied by source coverage”, never “observed to execute”. Butterfly says so in the footer of every page that shows the projection and in every exported report. The footer follows the overlay: with a trace imported and Measured selected it says the colours are measured, from which trace, and what a trace still does not show; with no overlay it says that none is applied. Its first job is to list every place the projection cannot be trusted. Those places are called gaps.

Feed it an execution trace and the same views switch to measured: real per-instruction counts, real branch outcomes, and a disagreement count wherever the projection said one thing and the hardware did another. Measured evidence is strictly stronger, and it is the practical route to Level A for Rust, where the compiler no longer emits MC/DC records at all.

Why this matters in one screen

The C example compiles the same function at four optimisation levels. Source coverage is identical at all four — 57 of 69 lines, 27 of 34 branches. The object code is not:

clamp_altitudeObject blocksGapsWhat happened
-O08noneThe object CFG mirrors the source
-O1 · -O2 · -Os12 predicated-decisionCompiled branchless with two csel instructions — the source decisions have no object branch to cover

A coverage percentage cannot see that difference. That is the argument for object-code analysis at Level A, and butterfly's reason to exist.

The one trap worth knowing

A raw profile carries a format version that llvm-profdata must match exactly. Mismatch it and you get raw profile version mismatch … no profile can be merged even though the file is right there. If you instrument with a system clang, point the scripts at that clang's own LLVM: LLVM_BIN=/usr/lib/llvm-18/bin ./examples/c/build.sh. Instrument with nightly Rust, use nightly's tools. CI does exactly this.

Platform notes

  • macOS keeps debug info in the .o files behind a debug map. A single-step compile-and-link runs dsymutil for you; a link of separate objects does not, and without the .dSYM the binary has no line table and every instruction lands in “no source line”. Run dsymutil <binary> after linking.
  • Linux keeps DWARF in the binary. No extra step.
  • Cross and bare-metal targets need nothing to run on your machine. Butterfly reads the export, the binary and an optional trace, so a target image analysed from a QEMU or hardware trace works the same way.

The workflow

Three commands from a build directory to a browser. Everything else is optional depth.

  1. Build twice

    Once instrumented, to get coverage. Once clean — that is the object code under analysis. The split is the whole point: instrumentation changes the code, so it must not be the code you certify.

    ./examples/c/build.sh

  2. Ingest

    Artifacts become one evidence.json. Note that -o defaults to the current directory, not the build directory.

    butterfly ingest examples/c/build --source-root examples/c \
    -o examples/c/build/evidence.json

  3. Browse

    A local, loopback-only viewer. Several evidence files become switchable variants with a Compare page.

    butterfly serve examples/c/build/evidence.json   # http://127.0.0.1:8787/

For a re-certification answer, add the two commands that turn history into work: butterfly changes … --since <certified baseline> then butterfly impact … --fail-on blocker. Both are covered under Change impact.

Gap kinds §6.4.4.2.b

A gap is a place where source coverage cannot describe the object code. Nine kinds, each with a specific cause.

KindMeaning
predicated-decisionA source decision compiled to conditional-select, a table or merged code with no object-level branch — branch coverage has nothing to map onto.
extra-object-branchMore conditional branches in the object code than branch regions in the source on that line.
line-zeroDWARF maps the instruction to line 0 — compiler-generated.
no-source-lineThe instruction has no line-table entry at all.
helper-callA call outside the covered source set, classified as runtime-check (panics, bounds and stack checks — defensive, not dead code), arith-helper, memory-helper, core-lib, libc or project-uncovered.
indirect-branchA jump table, tail call or function pointer: the target set must be established by analysis. A switch’s jump table is read from the image and its targets drawn as edges, so for a switch what is left is to confirm the table is the switch’s (examples/c-switch).
not-instrumentedMaps to a source line that carries no coverage count.
shared-lineA block whose instructions borrow source lines that do not describe it — a merged return or common epilogue. Reached only through a never-taken outcome, it is projected uncovered where line counts alone would mark it covered; entered unconditionally from a block that ran, it is projected covered where its borrowed line reads 0 (#270). Either way an inference, with the reasoning in the block note.
folded-callA call written in the source with neither a call instruction nor an inlined subroutine in the object code: the compiler evaluated it away.
uncounted-variantA C++ constructor or destructor variant the compiler emits beside the body (C1, D1, the deleting D0). It has no coverage counter of its own, so while the body ran, whether it did is not established: its instructions are projected unknown, not covered.

The other analyses

Stack §6.3.4.f

Frames come from -fstack-usage files, a .stack_sizes section, or prologue analysis when neither exists. Worst case is own frame plus the deepest chain of resolved direct calls. Recursion, indirect calls, dynamic frames, undetermined frame sizes, chains deeper than the analysable depth and overflowing totals are reported unbounded — never estimated.

Data coupling A-7 obj 8

Address-forming instruction sequences are decoded per architecture to find which globals each function reads, writes or takes the address of — and the Overview shows the reverse: every global with all of its accessors.

Dead code §6.4.4.3.c

A symbol is a candidate when nothing calls it, nothing takes its address (in code or data tables) and it is not the entry point. Executed-in-trace candidates are reported separately: they are reached by a path static analysis cannot see, so the mechanism must be identified.

Inlining & folded calls

DWARF inlined subroutines are attributed to their origin, so an inlined callee's instructions are not silently credited to the caller. A source call with no object counterpart at all becomes a folded-call gap.

Function pointers

Indirect call sites get static candidates from address-taken symbols and data tables, and resolved targets from a trace. Mach-O chained fixups are decoded, so vtables and dispatch tables resolve rather than vanishing.

Instantiations

llvm-cov emits one record per instantiation — a template at several types, or a crate compiled twice. Records sharing a name and source range are merged, with counts and MC/DC vectors summed, and the count shown on the function header.

Change impact §12.1.1

Recertification is where the money goes, and the expensive question is: what must I re-verify after this change? Butterfly answers it from the repository, the requirement tags and the evidence you already have.

commit message ──regex──> ticket
commit ────git log -L────> function          (follows drift and renames)
function ───@satisfies───> requirement
function ──gaps / MC-DC / review / baseline──> verification state

The first three hops are the trace. The fourth is what makes it impact analysis rather than a changelog: ticket FCS-104 touched clamp_i32, which implements LLR-UTIL-001, whose source-to-object review was signed off against the old object code and is now void.

How attribution works

For every function, git log -L <start>,<end>:<file> lists the commits that touched its lines. -L follows the range through later edits above it and through file renames — which mapping diff hunks onto today's line numbers cannot do, because a single insertion above a function invalidates it.

Two things a walk over today's functions cannot see are found otherwise:

  • Deleted functions. The frozen baseline records where every certified function was. For one that no longer exists, git blame --reverse gives the last commit its lines existed in, and the first commit after that to touch the file is the one that removed it.
  • Files with no functions. Every commit's --name-status is kept, so a ticket that changed only a header, a linker script or a build file — code that alters every includer's object code without touching a function — is not invisible.

Added is told from modified by reading each commit's diff of the function's own range: the oldest commit whose diff adds the signature line is the origin. A whole-file search is fooled by an identical signature elsewhere in the file — two types with the same fn new — which on a real 539-function kernel gave the wrong origin for 15 of them.

A deliberate limit

Coupling is reported one hop out. Whether it propagates further is an architectural judgement about your system, and the tool does not make it for you — it says so in a caveat instead of guessing.

The ticket view

Each ticket lists what it added, modified and deleted, plus every file its commits changed with the net status over the ticket and whether any function lives in it. On the Overview, in the report's Change impact section, and in impact --json. Commits with no ticket get their own table — code changed outside change control is a finding in its own right.

Staleness

The evidence records the HEAD its history was read at and the SHA-256 of every analysed source. serve compares both against the machine it runs on and counts resolutions written since the obligations were computed. If the repository moved on, a source changed on disk, a file has uncommitted edits, or a resolution was written, the Overview, the Changes tab, the top bar and the startup log say so — with the exact command to run. Stale attribution is never presented as current.

A source that cannot be read counts too, and is reported apart from one that changed: missing when it is no longer on this machine, unreadable when the read failed for another reason, each naming the file and why. Neither is a match. Treating a failed read as one is how a deleted source used to leave the attribution looking current — “we could not tell” is not “it still agrees”. Both are judged only inside the approved source root (--source-root). A source the evidence places outside it is a third case, not checked: it is never opened, and it gets the same answer whether or not it exists, so the check reveals nothing about files there (#248). Viewing evidence away from the tree it was built from therefore puts every source in that third category, which counts as stale and says to serve with --source-root at the tree the evidence was built from.

Analysis baseline §4.4.2.c

A new compiler, new options or new source constructs invalidate earlier coverage and traceability analyses. butterfly baseline freezes the environment and a per-function fingerprint — source hash, constructs, instruction and block counts, and where the function was. Keep it under configuration management.

An ingest given the baseline with --baseline compares against it and reports what changed: compiler, flags, architecture, constructs, and which functions changed in source or in object code — for a C++ constructor or destructor, in any of the variants the compiler emitted for it (#280). A butterfly-baseline.json left in the build directory it reads is discovered and compared the same way, without the flag (#238, fixed by #241); an ingest with neither does no comparison at all. Review records made before a change are marked STALE, and a red caveat bar sits above the whole page.

Source revision provenance

Every ingest records which revision of the project's sources the evidence came from, in provenance.sourceRevision, and whether the files the build used are that revision's files. Git and SVN (#301) are read.

It also records which build of butterfly wrote it (#117): provenance.toolCommit is the commit of butterfly's own sources the tool was built from, and provenance.toolDirty whether its work tree had uncommitted changes at the time — captured when the tool is compiled, printed by butterfly --version, and shown beside the version in the report and the Provenance panel. A build that is not from a checkout records unknown rather than guessing; evidence older than the field reads commit not recorded, never as a clean build.

The revision id is a label; the file hashes are the proof. butterfly does not ask git whether the tree is clean. For each file the build used — the coverage file list plus the files the DWARF line tables name — it computes the git blob id from the bytes ingest read and hashed, and compares it with HEAD's tree. assume-unchanged, skip-worktree and fsmonitor, which can make git status say clean, change nothing. An untracked generated header that was compiled in counts; an edited README does not, and is counted separately.

Never read as clean.

SVN. The revision is svnversion's (1234, or 1230:1234 in a mixed-revision working copy) with the repository UUID and ^/ path from svn info, since a number alone names neither repository nor branch. SVN's base checksums are of each file's normal form — keywords unexpanded, line endings LF — so a file with no svn:keywords, svn:eol-style or svn:special is compared with its base checksum by the bytes ingest read, which catches an edit svn status misses when the timestamp is put back; a file with one of them is judged by svn status alone, and the record counts which files were judged which way (svn.hashVerified, svn.statusOnly). A mixed revision, switched paths and a sparse checkout are recorded and named in the caveat even when clean; an external holding build files is judged as its own working copy, with its own revision. Every svn call is local (--non-interactive, never -u), bounded, with the environment cleared, and reads --xml.

Files outside the working copy — a vendored SDK, system headers — are listed as not under version control, not as modified. Git runs bounded (#246) as git --no-optional-locks -c core.fsmonitor=false with the GIT_* variables cleared; a recorded remote has its credentials removed. A modified or unknown state is a caveat, not a failure; the opt-in check --require-clean-source is #303.

Configuration butterfly.toml

Sits next to your sources and is picked up automatically.

# which requirement tags to look for
[requirements]
patterns = ['@satisfies\s+([A-Za-z0-9_.:/-]+)', 'REQ-[0-9]+']
scope    = "both"      # header | body | both
lookback = 30          # comment lines above a function to scan

# which tickets to recognise in commit messages
[change]
patterns = ['\b([A-Z]{2,10}-\d+)\b', 'refs #(\d+)']
exclude  = ["vendor/**", "generated/**"]

Capture group 1 is the identifier, or the whole match when the pattern has no group. The patterns in force are recorded in the evidence provenance, so a reviewer can see exactly how tags were found.

Set this first

The built-in ticket pattern is Jira-style ABC-123. It is deliberately narrow and still matches things like DO-178 or UTF-8 in a message — which is why every ticket found is listed for a human to sanity-check. The [change] pattern for your tracker is the single most consequential line in the file.

Report and CI

The report

butterfly report writes one self-contained HTML file — no external assets, safe to email. Thirteen sections, numbered in the order they appear: summary against table A-7, requirements coverage, the analysis baseline, build and provenance with input hashes, functions, compiler-generated code, gaps and their resolutions, coverage justifications (every fn:, line:, branch: and cond: review, with what it justifies), source-to-object traceability with CAST-12 sample adequacy, dead-code candidates and the image, stack usage, change impact, and caveats. Dead-code candidates, stack usage and change impact appear only when the evidence carries them; the numbering closes up around one that is absent, so cite a section by its title.

Gating a pipeline

butterfly impact evidence.json --fail-on blocker   # exit 3 if any blocker
butterfly changes evidence.json --since v1.2.0 --fail-on major

Exit 3 means the threshold was exceeded — 1 is an error, 2 a usage mistake — so a pipeline can gate without parsing anything.

Butterfly's own CI

Every push and pull request runs on Ubuntu (ubuntu-24.04; the macOS leg was removed in #147 because a macOS runner bills at roughly ten times a Linux one, so macOS is covered by scripts/ci-local.sh on a developer's machine and not by CI): full-depth checkout (the change tests read history), the pinned toolchain, the C example built first so the end-to-end and CLI suites run rather than skip — and the run fails if any suite reports “skipping” — then the documented ingest → summary → baseline → changes → impact → report workflow end to end, plus cargo audit, with warnings treated as errors.

What it will not claim

The honesty features are the product. Every one of these is a caveat on the evidence rather than a silent guess.

  • Projection is not measurement. The footer of every page says which of the two its colours are, and every report says it too.
  • Rust has no MC/DC. Current nightlies accept -Zcoverage-options=branch|condition but reject mcdc; stable emits no branch regions at all. So nothing invents pairs — but nothing announces the reason either: a Rust function's decision list is empty, and the MC/DC tab falls back to its generic “Branch regions without MC/DC records” table, or to “No decisions in this function.” The measured route via a trace is the practical answer.
  • Uncommitted edits. A file matching the working tree but not HEAD was built from uncommitted changes, so the line ranges used to attribute commits may be shifted.
  • A different checkout. A file matching neither is named, and the evidence says so.
  • Shallow clones. Flagged, because every function's earliest visible commit is then the clone boundary rather than its origin.
  • Squashed or rebased history collapses tickets into whichever commit survived. Not recoverable from git, so not pretended.
  • Split or merged functions keep only the history of the lines they have now; a renamed function appears as deleted plus added — which is what its tests and callers see.
  • Older LLVM. clang 18 exports MC/DC records without outcome counts or test vectors. Both layouts are read; the older one yields an empty truth table and a caveat.
  • Exploratory builds are stamped as such throughout. They exist to show what the optimiser did, never for credit.

Security posture

butterfly serve is a local viewer, unauthenticated by default, over data containing the complete source of your project. The defences follow from that:

  • Loopback by default. A non-loopback bind is refused unless you pass both --allow-remote and --insecure-http. The second flag acknowledges that the built-in server has no TLS, so the evidence and any bearer token cross the network in clear. Prefer an SSH tunnel, or a TLS-terminating reverse proxy. A proxy on the same host needs neither flag, because butterfly can stay on loopback.
  • One variant, one sidecar. Serving several evidence files gives each its own resolutions file, named from the variant plus a digest of that name. The digest is what makes the mapping injective: sanitising alone sent a/b and a_b to one file, and anything past 64 characters to the same prefix, so two variants could overwrite each other’s review decisions — and a hostile evidence file could aim at another variant’s sidecar on purpose. Duplicate variant names, and any two variants that would share a sidecar, are refused at startup before a single one is read.
  • Host-header allow-list. Without it, any web page you visit could reach the port by DNS rebinding and read the evidence.
  • Content-Security-Policy, nosniff and no-referrer on both the viewer and the report — the standalone report carries the policy in a <meta> tag, so injected markup stays inert even in a file mailed to a reviewer.
  • Bounded reads. Every artifact ingest reads — the coverage export, each source, objects, traces, the auxiliary files — is sized before it is read, against a per-kind cap and a budget for the whole run, as are the evidence and the resolutions sidecar serve loads. A crafted or truncated input fails with a sentence naming the file rather than by exhausting memory, and discovery classifies an unknown file by its magic number instead of reading it whole to find out. The defaults are generous, and every refusal names the BUTTERFLY_MAX_…_MB variable that would have let it through. The same readers also size the evidence butterfly tags and butterfly claims read (evidence cap), the requirements sidecar claims reads and the config butterfly build reads (auxiliary cap), the requirement documents serve re-hashes at startup (auxiliary cap, sharing the sidecar’s budget), and each analysed source /api/freshness re-hashes (source cap, one budget per request) (#231). A BUTTERFLY_UI_DIR override is read under the auxiliary cap too.
  • Helper programs run under one policy. Every program butterfly runs on its own behalf — git, llvm-objdump, llvm-cov export, ctags, rustc and the compiler’s probes — runs by the absolute path it resolved and records, with the environment cleared to a short allow-list (no GIT_DIR, no token), a deadline (BUTTERFLY_HELPER_TIMEOUT_SECS, default 600) and a ceiling on each stream (BUTTERFLY_MAX_HELPER_OUTPUT_MB, default 4096, on stdout; 1 MiB of stderr). Past either it is stopped at once, with whatever it started. At most BUTTERFLY_MAX_HELPERS run at a time. A tool you configure (--llvm-bin, BUTTERFLY_LLVM_BIN, --ctags-bin, BUTTERFLY_CTAGS) is used or refused, never swapped for another copy on PATH. Your own build commands are not helpers and are not bounded (#246).
  • Evidence is validated on load. Every index is range-checked and a foreign schema rejected: a truncated or hostile file gives a named error, never a panic mid-render.
  • Names from data never shape file paths, and counters saturate so a corrupt trace cannot overflow a count.
  • Source reads are bounded by --source-root (the working directory when you do not pass one). A coverage export’s filenames are input like any other, and every source butterfly reads is embedded whole in the evidence you then serve and archive — so each name is resolved, symlinks and .. included, and ingest fails, naming every offender, if one lands outside the root. A source with more than one name (a hard link) is refused the same way, because the kernel reports only one of a file’s names and whether every name is inside the root cannot be established. Generated or vendored sources elsewhere are read only under --allow-external-source, which records a caveat saying which files came from outside.
  • The viewer’s freshness check reads only what you approved. The evidence names its sources and its repository, and the evidence is input like any other. A source is read only if it is inside --source-root (default: the working directory for serve, the project for run, the config’s source root for build), placed by the kernel as ingest does; git runs only in --repo (default: the repository containing the source root), because a repository’s own config can make git run a program. Anything else is reported as not checked — stale, never opened.
  • Outputs are replaced, never truncated. The evidence, the change cache, the report, the baseline and every sidecar are written the same way, relative to one descriptor for the destination’s directory. Each write goes to a temporary file beside it, is flushed to disk, then renamed over the top — so a reader sees the old document or the new one, never half of one, and an interrupted or failed write leaves the last complete document intact. Rename replaces the destination entry itself, so a symlink planted there is displaced rather than written through. The temporary is created exclusively under a name that cannot be guessed, so preplanting it as a link fails the open instead of truncating its target; butterfly says so on stderr and leaves the link’s target untouched.
  • Expensive work is bounded. The report, the freshness check and the gates run off the async threads, at most four at a time. Past that they get an immediate 503 with Retry-After, and the cheap routes are unaffected. The report is cached until a review changes it, and freshness for five seconds. No request is held open for more than a minute. Per-client rate limiting belongs in the reverse proxy in front, with TLS.
  • A network listener needs a token, read-only included. Without one butterfly refuses to start, unless you pass --allow-unauthenticated-remote. That flag serves reads to anyone who can reach the port, and resolution writes come back 403 with the way to enable them. The token comes from exactly one of --token-file <path>, BUTTERFLY_TOKEN or --token generate. A literal --token <secret> still works but is deprecated, because it is visible in the process list. The token is then required on every API route, reads included. The viewer asks for it in a password field, or takes a minted one from the #token= fragment of the link butterfly prints; a browser never sends a fragment, so the token is never in a request target. A ?token= URL is refused. --read-only refuses writes on any address. Loopback with no flags is unchanged. Authorization is attached to the routes, not inferred from the bind address, and startup prints the exposure and the authentication mode every time.
Treat these like a Makefile

butterfly build runs the commands in your build config, and ingest runs llvm-objdump from your toolchain. Only run them on projects you trust. Evidence files embed absolute paths, the build host name and the full source text. A report carries less — the paths and hashes of its inputs, and any requirement text — but neither the host name nor the source. Redact before sending either outside your organisation.

Qualification §12.2, Table 12-1

Butterfly is a browser over evidence, not a producer of certification credit. The criteria and the level are the applicant's determination for their own intended use, recorded in the PSAC, and not properties of the tool: a claim limited to the objectives butterfly automates is DO-178C §12.2.2 Criteria 3, which Table 12-1 puts at TQL-5 for Levels A to D. Review of the output by a human is what keeps the claim at Criteria 3 rather than Criteria 2; it does not remove the need to qualify the tool that computed it.

Nor is the qualified set the ingest parser alone — the viewer and the report present what ingest produced, and a project claiming credit from what they show is claiming credit from them. The exploratory-build function (butterfly build) is the one that must be excluded, because its output is object code. The project's own analysis of what a TQL-5 package would take is docs/qualification/DO-330-assessment.md.

The line to hold

The moment butterfly is presented as replacing a verification activity — rather than helping a human perform one — the DO-330 burden lands in full. Every caveat, every “projected, not measured”, and every refusal to guess exists to keep that line clear.
